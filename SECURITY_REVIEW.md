## Производительность

- Товары: удалены отдельные aggregate рейтинга и filter/first изображений на каждый товар. В тесте список из 1 и из 9 товаров выполняет одинаковые **2 SQL-запроса**, без авторизации.
- Добавлены select_related/prefetch_related для корзины, избранного, подборок, заказов, новостей, фотографий/сертификатов мероприятий.
- Главная использует заранее выбранные популярные курсы; фильтрация больше не обходит prefetch cache.
- Курсы загружают школу, тег, файлы, модули и заявки текущего пользователя пакетами.
- Добавление в корзину использует транзакцию и блокировку корзины; уникальность пары cart/product дополнительно обеспечивается БД.
- Это проверка количества запросов и поведения. Нагрузочный тест production и измерение p95 не проводились.

## Что остаётся закрыть отдельно

### P1 — резервирование склада до оплаты

Проверка остатка при оформлении не резервирует товар. Два pending-заказа могут оплатить последний экземпляр. Изменение предотвращает отрицательные остатки и сохраняет факт успешной оплаты, но при нехватке пишет ошибку о необходимой сверке склада. Нужны резерв при создании заказа, освобождение при отмене/истечении срока, обработка оплаченной нехватки и тесты конкуренции на PostgreSQL.

### P1 — неопределённый результат создания платежа

Заказ теперь сохраняется при timeout, но автоматической сверки неизвестного payment_id и повторного запроса по постоянному idempotency key пока нет. Платёж, принятый провайдером перед сетевым обрывом, требует сверки по metadata.order_id. Нельзя считать ответ 502 доказательством отсутствия списания.

### P1 при публичной раздаче media — прямые ссылки на учебные файлы

API ограничивает раскрытие материалов, но FileField по-прежнему возвращает media URL. Если production Nginx/CDN раздаёт files/ публично, знание URL обходит проверку участника. Production-конфигурация не проверялась. Нужны private storage и авторизованная выдача через приложение/X-Accel-Redirect или краткоживущие подписанные URL; публичные картинки каталога при этом должны остаться доступными. Одной проверки сериализатора недостаточно.

### P2 — production-развёртывание и защита от нагрузки

- В docker-compose.yaml запущен runserver, наружу опубликованы 8000 и 5432. Если этот файл используется в production, нужен production WSGI-сервер, сетевые ограничения и актуальные закреплённые образы.
- settings.py фактически использует SQLite, хотя compose поднимает PostgreSQL. select_for_update в SQLite не обеспечивает блокировку строк. Переход на PostgreSQL требует переноса существующих данных, а не простого переключения DB_HOST.
- Throttle регистрации/входа использует стандартный cache Django и является ограничителем на процесс; это не полноценная защита от распределённого перебора. Нужны общий cache и/или rate limit на доверенном reverse proxy. NUM_PROXIES=1 должен соответствовать реальной топологии.
- Nginx разрешает тело до 3048M. Нужны отдельные лимиты API и административной загрузки файлов, проверка типов/размеров, квоты.
- Большие публичные списки по-прежнему без пагинации. Следующий этап — пагинация с обновлением клиентов и нагрузочным тестом.
- Уведомление Telegram синхронное после commit; при сбое нет очереди и гарантированного повторения.
- Токены хранятся в localStorage. Подтверждённой пользовательской XSS в просмотренном потоке не найдено, но при её появлении токены доступны JavaScript. Для дальнейшего усиления нужны продуманная CSP и оценка перехода refresh на HttpOnly cookie с CSRF-защитой.
- Повторная отправка письма и отправка при регистрации синхронны. Для большого потока нужны очередь/повторные доставки и защита от почтового спама.

## Внедрение

1. Сделать резервную копию БД и проверить email-дубли без учёта регистра. Миграция намеренно останавливается при конфликте, не объединяя разные аккаунты.
2. Настроить длинный случайный DJANGO_SECRET_KEY, SMTP, DEFAULT_FROM_EMAIL и FRONTEND_URL. При использовании старых/опубликованных значений сменить ключи и проверить, не использовались ли опубликованные реквизиты. Удаление значения из последнего коммита не удаляет его из истории Git.
3. Настроить SPF/DKIM/DMARC у отправляющего домена. Отрисовка письма проверена в браузере; реальная доставляемость и отдельные версии Outlook требуют проверки через выбранный почтовый сервис.
4. Установить зависимости и выполнить python manage.py migrate. Миграция объединяет дубли CartItem только для той же корзины/товара и удаляет нулевые позиции; нужна резервная копия.
5. Развернуть backend и frontend согласованно. Старые JWT без refresh_jti больше не принимаются. Существующим покупателям нужно подтвердить email через повторное письмо; существующие staff-аккаунты миграция сохраняет подтверждёнными.
6. Периодически запускать python manage.py flushexpiredtokens.
7. Перед боевой оплатой закрыть описанные риски резервирования/сверки платежей и проверить реальные SMTP/платежи в тестовом окружении.
